    1The question

    Can classical machine-learning models estimate the probability that a Codeforces user will solve a problem from their rating, contest performance, submission history and the problem’s difficulty and tags? And can those estimates identify weak topics and recommend problems at an appropriate difficulty?

    One row

    A user–problem interaction, created when the user first submits a solo solution to that problem.

    Target

    1 if the user gets an accepted submission on that problem within 30 days of the first attempt, otherwise 0.

    When the prediction is made

    Just before that first submission. Every feature uses only submissions and rating changes from strictly earlier.

    What a useful answer looks like

    Better-than-baseline ranking and well-calibrated probabilities on a later time period, and recommendations that beat simple rating-based selection. Nothing here is causal.

    2Data

    All data comes from the official Codeforces API with Python requests, using the public endpoints user.ratedList, user.info, user.rating, user.status and problemset.problems. We sampled 80 rated users from each of five rating bands and downloaded their complete submission histories, spacing requests 2.1 seconds apart and caching every response.

    Key variables

    • Submissions: user, problem, time, verdict (Accepted, Wrong Answer and so on), participation mode (contest, practice, virtual).
    • Problems: difficulty rating (800–3500) and topic tags such as dp, greedy or graphs.
    • Rating history: the user’s rating before and after every rated contest, with its date.
    • Target: whether the problem was accepted within 30 days of the first attempt (94% yes).

    Cleaning and quality checks

    • All 400 histories were paginated back to the first submission, so a user’s first attempt really is their first.
    • Team submissions and submissions without a problem ID were dropped, and handles were lower-cased before joining.
    • Only rated problems are modelled, because difficulty is central to the question and to recommendations.
    • An interaction is kept only if its whole 30-day outcome window is observed before collection ended. Problems a user never attempted are never treated as failures.

    What the training data shows

    Loading…

    The headline fact is that 94% of attempted problems are solved within 30 days. Users mostly start problems they can finish and keep retrying, so “not solved” is the rare and informative outcome. Solve rates still fall steadily with relative difficulty, from 99% for problems far below a user’s rating to 85% far above. Graph and data-structure problems are solved least often.

    3Features and preprocessing

    Each user’s history is replayed in time order, like a film. Every time the user starts a new problem, we take a snapshot of their record at that moment, and only then update it. This gives 47 features per interaction, all computed from events strictly before the first attempt, so the model sees exactly what would have been known when the prediction is made.

    GroupFeatures
    Rating and contestsRating before the attempt (1400 if unrated, plus a flag), maximum rating, number of rated contests, last rating change, mean of the last five changes, days since the last contest
    DifficultyProblem rating, rating gap (problem − user), Elo expected score 1 / (1 + 10gap/400)
    Submission historyProblems attempted so far and in the last 30 days, days active, overall solve rate, solve rate within ±200 rating of this problem
    TopicsSolve rate on the problem’s tags (mean, minimum, relative to overall), experience in the least-practised tag, 25 tag indicators

    Preprocessing choices

    ChoiceWhy
    Only past events per rowPrevents leakage; unit tests check that future submissions never change past features
    Beta(1, 1) smoothing of solve ratesOne lucky solve should not read as 100%
    “Unsolved as of that moment”A later solve was not known at prediction time
    Log transform of countsCounts are very skewed; very active users would dominate
    Scaling inside a pipelineLearned from training rows only (needed for Logistic Regression)

    The most delicate choice is time. If a user tried problem A on Monday, tried B on Tuesday and solved A on Wednesday, then at the moment B starts, A counts as attempted but not yet solved, because that is all that was known on Tuesday. Using the final outcome instead would quietly leak the future into the features and inflate every score. Smoothing matters for the same reason: a user with a 1/1 record in a topic has shown very little, so the rate is pulled toward 50% until more evidence arrives.

    4Baseline and methods

    ModelHow it worksWhy we use it
    Baseline (rating gap)Elo expected score from the user–problem rating difference; nothing is learnedThe rule from our proposal: “pick problems near your rating”. Any model must beat it
    Logistic RegressionWeighted sum of features turned into a probability; C tunedInterpretable; shows how far a linear model gets
    Random ForestAverages many deep trees; depth and leaf size tunedCaptures non-linear effects and interactions
    Gradient BoostingTrees built one after another, each fixing earlier errors; learning rate and tree size tunedUsually the strongest classical model on tabular data

    Why this baseline. It is meaningful rather than trivial: it uses the strongest single pattern in the data (how hard the problem is relative to the user) and is exactly the rating-based selection that our recommendations are later compared against. If personal history adds nothing, the models should not beat it.

    Why these models. They form a ladder of flexibility. Logistic Regression tests whether straight-line effects are enough. The two tree ensembles test whether interactions matter, for example a rating gap of +300 meaning something different for a beginner than for an experienced user. More complex is not automatically better, so every model had to earn its place on validation data.

    5Evaluation design

    The data is split by time, so the model always predicts the future from the past. The split was fixed before any modelling.

    PartPeriodRowsUsed for
    TrainBefore Jan 2025–Fitting every model
    ValidationJan 2025 to Oct 2025–Choosing settings, model and threshold
    TestAfter Oct 2025–Scored once, at the end
    1. Split by time, fixed before modelling. Real use means predicting the future from the past, so a random split, which would let the model learn from 2026 to “predict” 2023, would be too optimistic.
    2. Embargo. A training or validation row is kept only if its 30-day outcome window closes before the next period begins (7,383 rows dropped), so no label depends on events in a later period.
    3. Tune on validation. Every configuration is fitted on training rows and compared by validation ROC-AUC. The test period is never looked at.
    4. Test once. The chosen configuration of each family is refitted on training plus validation and scored a single time on test.

    Metrics

    MetricWhat it tells us
    ROC-AUC (main)Chance a solved problem is ranked above an unsolved one; 0.5 is a coin flip
    Precision (not solved)When the model warns “likely unsolved”, how often it is right
    Recall (not solved)How many of the truly unsolved problems it catches
    F1 (not solved)One score balancing precision and recall
    AccuracyShown but not trusted: predicting “solved” for everything is already 94% accurate
    Cross-entropyWhether the probabilities are honest; lower is better

    Why these metrics. ROC-AUC is the main one because recommendations depend on ranking problems correctly. Only 5.7% of test rows are unsolved, so accuracy rewards a model that ignores them, which is why precision, recall and F1 are measured on the rare “not solved” class. Their threshold is chosen on validation and frozen before testing. Because the tool shows probabilities to users, cross-entropy and a calibration chart check that a 90% estimate comes true about 90% of the time. All 95% intervals come from resampling whole test users, so one very active user’s rows move together.

          8Skill gaps and recommendations

          How we tested model-based skill gaps

          For problems near a user’s rating, we compared the model’s estimate using their real record in a topic with the estimate after replacing that record by their overall one. This isolates personal weaknesses from topics that are hard for everyone. Because the test below found these gaps add little, the tool shows each user’s plain record by topic instead.

          How problems are recommended

          Among unattempted problems in the chosen rating range and topic, the default list shows the hardest ones the model still gives at least an 85% chance of being solved, a stretch that is likely to pay off. Each suggestion explains its difficulty, the relevant record and how similar estimates turned out.

              9Limitations

              • Self-selection. We only see problems people chose to attempt, which is why 94% are solved. Estimates for problems far from a user’s usual choices are extrapolations.
              • Sample. 400 rated users balanced by rating band, not a random sample of Codeforces. Prolific users contribute many more rows and so more weight.
              • Snapshot metadata. Problem ratings and tags were fetched in 2026. Older attempts may have seen different values, and ratings are partly derived from how many people solved a problem.
              • Target definition. A solve after twenty wrong submissions counts the same as a first-try solve, and 30 days is a choice. Other windows would shift the base rate.
              • Skill gaps did not add predictive value beyond overall skill and difficulty. Recommendations were tested offline on users’ own choices, not in a controlled experiment.
              • Change over time. The test year may differ from earlier years, for example through AI-assisted solving, and relationships learned from the past may weaken.

              10Conclusion

              Classical models estimate solve probability well beyond the rating-gap rule.

              11Reproduce

              The source repository on GitHub includes the collection code, the processed data tables, the analysis notebook, tests, and the pipeline that writes every number on this page.

              1. pip install -r requirements.txt
              2. Optional, several hours: python -m src.collect --config config.json recollects the raw data from the API. The processed tables are already included.
              3. python -m src.pipeline builds the dataset, tunes and tests all models, evaluates skill gaps and recommendations, and exports this site’s data. Or run notebooks/skill_gap_estimator.ipynb for the same steps with plots.
              4. python -m pytest tests and node tests/check_parity.mjs check the feature engine and that this page reproduces Python’s predictions exactly.
